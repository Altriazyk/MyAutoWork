# myautowork

一个**以插件为核心的 Windows 自动化运行时**。

打开软件看到的是**我的流程列表** —— 点一下就跑，不用先进画布。所有具体能力
（界面操作、文件、网络、时间……）都由插件提供，插件跑在独立进程里。

![首页：我的流程列表](docs/screenshot-home.png)

> **进度**
>
> **第 1 步（地基）** ✅ 内核、插件契约、双线执行引擎、运行历史、命令行运行器
>
> **第 2 步（图形界面）** ✅ 流程列表首页、自绘画布编辑器、schema 驱动的表单、运行态可视化
>
> **第 3 步** ⬜ 界面自动化三件套 + 元素拾取器

---

## 快速开始

内核和命令行**只用标准库**；图形界面需要 Qt。

```powershell
# 1) 图形界面（建议建一个独立 venv，别污染全局环境）
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install PySide6-Essentials

# 2) 打开软件 —— 停在流程列表
.\.venv\Scripts\python.exe -m host

# 3) 直接编辑某条流程
.\.venv\Scripts\python.exe -m host workflows\demo.json

# 4) 命令行（任何 Python 3.10+ 都能跑，不需要 Qt）
python -m kernel.run --list-workflows
python -m kernel.run --list-plugins
python -m kernel.run --validate workflows/demo.json
python -m kernel.run workflows/demo.json --workdir .

# 5) 测试
python tests\smoke.py                              # 内核 125 项
.\.venv\Scripts\python.exe tests\ui_smoke.py       # 界面 336 项（离屏渲染，顺带出截图）
.\.venv\Scripts\python.exe tests\uia_smoke.py      # 界面自动化 54 项（真实桌面，会弹个小窗口）
.\.venv\Scripts\python.exe tests\app_launch.py          # 入口 13 项（首页场景）
.\.venv\Scripts\python.exe tests\app_launch.py editor   # 入口 8 项（编辑器场景）
```

## 界面

### 窗口外壳

**没有系统标题栏。** 那一行本来只写着一个软件名，不如让给菜单 —— 最顶上一行现在就是
`文件 / 编辑 / 视图 / 运行 / 帮助`，右侧是窗口按钮。

代价是拖动和边缘缩放要自己接管：拖动走 Windows 原生的 `startSystemMove()`（贴边、
拖到屏幕顶端最大化这些行为全都白拿），边缘 6 像素在 `nativeEvent` 里接管
`WM_NCHITTEST` 交给原生缩放。任何一步出问题都直接放行 —— 缩放不可用不该让窗口打不开。

下面是左侧导航栏 + 内容区。导航栏只在"流程列表 / 插件"这两页出现；进编辑器后左边让给
模块面板，它自动收起。左下角只显示流程数 —— 插件数在插件页里一目了然，没必要到处重复。

**也没有状态栏。** 那条常驻横条没事的时候只是一行空白，而用户在画布或列表上操作时也不会
往下看。它原来承担的两件事各自安置到了更合适的位置：

- **连线反馈**浮在**画布底部**（`CanvasView.show_toast()`）—— 拖线的时候它就在眼前，
  这正是最需要看到"为什么连不上"的时刻
- **缩放比例**印在**工具栏那个缩放按钮**上，点一下复位到 100%
- 其余提示进**运行日志** —— 本来就在视野里，还顺手留了痕

### 首页：我的流程列表

![卡片视图](docs/screenshot-home.png)

用户打开软件看到的第一屏，也是一天里用得最多的一屏。它应该像**发射台**，不像编辑器。

左侧栏分三段：

| 分段 | 内容 | 说明 |
|---|---|---|
| 导航 | 我的流程 / 我的插件 / 我的模块 / 我的清单 | 四个页面 |
| 底部 | N 条流程 | 一眼知道有多少条 |

标题栏**最左边**（菜单之前）有一个 ☰ 开关，用来收/放左侧栏 —— 它管的是窗口左边那一整条，
放在最左才对得上位置；菜单管的是全局操作，是另一件事。编辑器里侧边栏本来就会自动收起
（左边让给模块面板），那是另一套逻辑，两者互不干扰。

### 插件依赖：共用一个虚拟环境

插件进程默认用**主 venv 的解释器**启动（`Manifest.python_executable()` 的兜底），所以插件的
第三方依赖装在项目 venv 里就行 —— 不需要每个插件建一个。

内置的三个界面插件依赖 `uiautomation` / `pywin32` / `pydirectinput` / `Pillow`，就装在主 venv。
`myautowork.uia` / `imaging` 里这些重依赖都是**延迟导入**的，所以没装 `uiautomation` 的机器
照样能用流程引擎，只在真去点界面自动化时才报错。

manifest 里的 `runtime.venv` / `runtime.python` 仍然支持（`自带 venv > 指定解释器 > 内核的`），
留给"两个插件分别依赖 requests 2.1 和 2.31"那种情况用，现在没人用。

### core.flow：流程控制

| 动作 | 作用 |
|---|---|
| 条件判断 | 比两个值。成立走 success，不成立走 **error 出口** |
| 设置变量 | 写工作流变量，后面用 `{{ $vars.名字 }}` 取；也能当计数器（相加 / 追加） |
| 写日志 | 往运行日志写一条，调试时最有用的一步 |
| 结束 | 一条分支到此为止的**标记**（什么都不做，就是让画面上一眼看出这里是有意停的） |
| 等文件出现 | 反复检查路径，直到它出现（可要求最小字节数） |
| 等程序出现 | 反复查进程名，直到它跑起来 |

**为什么条件要拆成「左值 / 运算符 / 右值」。** 表达式语言（`{{ ... }}`）只做**点分路径
取值**（`$node.n2.count`、`$vars.token`），它**没有** `>`、`==` 这些运算符。所以比较必须
由插件自己做：用户用表达式把两边的值取过来，运算符插件实现。

**「条件不成立」走 error 出口，但它不是出错。** 引擎给每个节点的执行出口只有
`success` / `error` 两个，没有自定义端口名。所以「条件判断」的 error 出口含义是**条件为假**。
为此加了 `myautowork.ExpectedError`：插件用它标记"这是预期之内的失败"，**内核只往日志写
一行、不打栈**；真有 bug 的异常照旧打完整栈。实测一条 false 分支的报错就是
`ConditionNotMet: 条件不成立：3 小于 3`，一行。

#### 循环：`if` + 回边

执行器**支持环**（有 `max_steps` 兜底）：

```
设变量 n = 0 ──> 条件判断 n < 5 ──success──> 正文 ──> 设变量 n = n + 1 ──┐
                        │                                                │
                        └──error──> 出口              回到「条件判断」<───┘
```

实测跑过：一个三轮循环执行了 **12 个节点**（n1 + 三次 if/正文/自增 + 最后一次 if +
结束），`n2` 恰好执行 4 次，运行状态 **`success`**。

**「条件为假」不会把整条流程标成失败** —— 这条是循环能不能用的地基，所以专门有测试盯着。
环的存在只报**警告**（`exec_cycle`），不判错误。

**为什么没有"反复求值的等待"。** 参数是在动作**被调用之前**求值一次的，动作里拿不到原始
表达式，所以 `wait_until(某项 > 3)` 这种做不到 —— 表达式不会重算。等待只能基于动作自己能
反复检查的**外部状态**，也就是「等文件出现」和「等程序出现」。

### core.app：启动程序

自动化开始之前的那一步常常就是"先把某个软件打开"（模拟器、微信、浏览器）。没有这个动作，
整条流程只能靠人手动点第一下 —— 这也正好是 `win.window` 那组动作的盲区：它们全都作用于
**已经存在的窗口**，程序没起来就无从下手。

| 动作 | 作用 |
|---|---|
| 启动程序 | 启动一个 exe，并且可以等它的窗口出现 |
| 关闭程序 | 按 PID 或进程名结束，默认连子进程一起 |
| 程序在跑吗 | 查进程在不在（也用来做"先关掉再启动"） |
| 用默认程序打开 | 像双击一样打开文件、文件夹或网址 |

**启动之后必须彻底断开。** `DETACHED_PROCESS` 加三个 `DEVNULL` 不是可选项：宿主是通过管道读
worker 的 stdout 的，如果被启动的程序**继承了那根管道**，宿主会一直等它关闭 —— 表现就是
"流程卡在这儿不动，直到你手动关掉那个程序"。Windows 上子孙进程继承句柄是默认行为。

实测过：子进程里启动一个活 9 秒的程序然后自己退出，父进程读到管道 EOF 只用了 **0.1 秒**。

**"等窗口出现"比"等 N 秒"靠谱。** 模拟器冷启动可能 8 秒也可能 40 秒。写死 sleep 要么白等
要么不够，真正的信号是那个窗口出现了。标题填错时**会把当前开着的窗口标题列出来**让你照着抄
—— 因为标题跟系统语言、软件版本都有关（同一个记事本，这台机器上显示的是
`无标题 - Notepad` 而不是中文），没法预设。

**两个已知限制。** 需要管理员权限的程序，普通权限启动会失败（而且系统不一定给得出明确提示）；
`启动程序` 返回的 PID 可能是**启动器**的，真正的程序是它拉起来的另一个进程 —— 想精确关掉它，
用「程序在跑吗」按进程名找。

### fgo：模拟器游戏自动化（示例插件，非内置）

`plugins/fgo/` 是一个**用户插件**的完整例子（所以它出现在「我的模块」页，可编辑、可删）。

**通道是 ADB，不是"截窗口 + 模拟鼠标"。** 模拟器里是正经 Android 系统，有对外接口。走窗口
那条路等于把渲染方式、窗口位置、缩放比全扛在自己身上 —— 用户拖一下窗口，整套坐标就废了。
ADB 拿到的是**设备坐标系**，跟窗口无关。

**截图用 `exec-out`，不用 `shell`。** `adb shell screencap -p` 会让 PNG 二进制流过一层 shell
转发，Windows 上那层做 CRLF 转换 —— 结果是**看起来存下来了、但打不开**的图（经典的
`0x0D 0x0A` 损坏）。

**adb 的查找顺序是 用户指定 > 模拟器自带 > PATH。** 模拟器自带排在 PATH 前面是被坑出来的：
逍遥启动时会用自己的 adb 起 server，这时从 PATH 拿一个版本不同的 adb 过来，它会先打印
`adb server version doesn't match, killing...`，**把模拟器的 server 杀掉再起自己的** ——
表现就是"刚才还好好的，一调用就掉线"。

**已经实测过的（逍遥 127.0.0.1:21503）**：找 adb、连接、读分辨率、读前台包名、截图
（700 KB，PNG 头校验通过）、模板匹配定位（`(624, 185)`，得分 `0.0`，3 ms）。
`com.bilibili.fatego` 是 `pm list packages` 查出来的实装包名，不是猜的。

**"眼睛"在 SDK 里，不在插件里。** `myautowork.imaging.find_in(image, template, threshold,
region)` 匹配**调用方递进来的那张图**，返回值就是那张图自己的坐标系 —— 对 adb 截图来说正好是
设备坐标，能直接交给 `input tap`。原来的 `find()` 是给 Windows 桌面写的（它自己调 `grab()`
截屏，还带一层 DPI 换算），拿它匹配模拟器截图会同时错两件事。

#### 一个躺了很久的 bug：粗找 -> 精调的坐标换算

粗找是在**缩小后**的图上滑模板，返回的是**格子坐标**。原代码直接把格子坐标当原图坐标用来算
精调区域 —— 2 倍缩小时精调会跑到一半的位置上找，永远找不到目标。

后果不只是"找不到"：精调扫错了地方，返回的要么是 None，要么是错误位置；而且白白扫一大片，
一次匹配要 **2.7 秒**。修完是 **3 毫秒**。

`find()`（桌面 UIA 拾取器的图像兜底）有**一模一样**的错误，一直是"运气好才管用" —— 因为
它总是先用"元素原来在哪"那把种子，种子命中时就轮不到精调出场。

`tests/smoke.py` 第 11 节是纯图回归测试（600×400 的画布 + 120×60 的纹理模板），不依赖屏幕也
不依赖模拟器，任何人跑测试都能挡住它再犯。

### 插件依赖：声明 → 检测 → 一键安装

manifest 里可以声明第三方包，pip 要求的写法：

```json
"dependencies": ["uiautomation", "pywin32", "Pillow"]
```

内核负责**检测**（`kernel/dependencies.py`），界面负责**让你点一下装**。

**只检测，不自动装。** 自动装意味着内核会在用户没点头的情况下联网、执行 pip、改他机器上
的环境。离线机器上那会变成一个卡住的进度条；装了别的东西的机器上，它可能悄悄升级掉别人依赖
的版本。所以内核只说清楚缺什么，装不装由用户决定。

**按钮在每条模块的卡片上，不在页面上。** 页面上放一个总的，用户还得回头去找是哪条模块缺；
而"装不装"这个决定本来就是针对具体某条模块做的。**插件页没有这个按钮** —— 那一页回答的是
"我现在有什么能力"，是只读展示；装依赖是对"我自己的东西"动手的操作，归「我的模块」页。

**装到"这个模块跑起来会用的那个解释器"里**，不是想当然用主 venv —— 插件自带 venv 时，装到
主 venv 等于装到了别处，用户看到"装好了"但模块照样起不来。

安装跑在**子进程 + QThread** 里：同进程跑 pip 会污染 `sys.path` 和已导入模块的状态（装完那些
模块还是旧版本，直到重启），而且不好取消。pip 的输出一行行流进运行日志。安装期间所有卡片上的
按钮都禁用 —— 同时开几个 pip 只会把环境搞乱。

**为什么按分发包名判"装没装"，不判版本。** 包名和 import 名经常不一样（`Pillow` → `PIL`、
`pywin32` → `win32api`），版本比对又需要 `packaging`。**不确定的事不假装确定** —— 报"可能缺"
比报"一定缺"诚实。

**也不靠"跑一下看报错"来检测** —— 那是在执行插件代码，等于让"看一眼"这个动作有了副作用。

### 深色 / 浅色主题

「视图」菜单 →「浅色主题」（`Ctrl+T`）。

实现上没有重写那一百行 QSS，而是**对调色板做字符串替换**：导入时那份深色 QSS 已经是字面量
了，切换时把结构色（背景 / 边框 / 灰阶文字）逐个换成浅色对应值。**语义色一律不动** ——
成功绿、失败红、分类色表达的是含义，换个主题也该是同一个含义。

画布上的东西是自绘的，颜色在 `paint` 时才读，所以只要让它重画一遍；各个页面则重建一遍
（它们本来就有 `reload()`）。

**那些模块级的样式常量怎么办。** 各页面里有一批 `_CARD_STYLE` 之类的常量，是**导入时**算好
的 f-string，里面冻的是深色值 —— 重建页面也没用，重建出来的还是那份老字符串。

与其在十几处 `setStyleSheet` 上各包一层（容易漏，而且以后新加的地方又会忘），不如**在源头把
常量本身改掉**：`set_mode()` 遍历已导入的 `host.*` 模块，把「末尾是 `_STYLE` 且含 `#`」的模块
级字符串按主题改写一遍。调用点一行都不用动，也不会漏。

两个细节：**深色原文要先快照下来**（改过之后再读它，读到的已经是换算后的值，来回切几次就糊
了）；收集时要排除 `_` 开头的名字 —— `"_DARK_HEX".isupper()` 返回 True（下划线不算大小写），
不过滤的话这两张表会把自己也收进去，切浅色时把"原值表"覆盖掉，就再也切不回深色了。

**白字贴白底。** 有几处规则写死了 `color: #ffffff`（选中的页签、选中的侧边栏项、切换按钮），
背景一变浅文字就没了。改成引用 `NODE_TEXT`，跟着主题一起走。

### 我的清单：建几份清单，一次跑完一份


![我的清单](docs/screenshot-checklist.png)
![新建清单](docs/screenshot-checklist-editor.png)

单条流程解决"一件事"，但真实的一天往往是"早上这一套"：导出报表 → 上传 → 发通知。挨个点
「运行」、等它跑完再点下一个，人就成了调度器。清单把这件事收进一个动作。

**清单拆成两页，和「我的模块」一个形态。**

- **「我的清单」只列出已有的清单** —— 每条一行：名字、N 条流程、运行中/结果，加上
  运行 / 编辑 / 重命名 / 删除。
- **「新建清单」开一个独立页面**（不是就地弹输入行，也不是模态框）：填名字 + 勾选它包含
  哪些流程，保存回到列表。

挤在一页里的话，"新建"和"我现在在看哪条"会互相打架：列表得同时承担选择器和编辑区两个
职责，用户也分不清那些勾选框到底属于哪条清单。

**每条清单自带「运行」。** 点哪条跑哪条，不用先切过去 —— 换个清单只为跑它一次是很常见的
用法；非要先切换的话，"当前选中哪条"就变成一个必须记着的心智负担。运行结果（`2/2 成功`）
标在那一行上。

**执行是严格串行的，不是并发。** 界面自动化会抢鼠标键盘、文件流程会抢同一个文件 —— 两条
流程同时跑，结果多半是互相踩。而且**顺序本身有意义**（先导出再上传），并发直接把这个语义
弄丢了。执行中按「停止」是停**整批**，不是"停一条、跑下一条"。

**坏掉的流程勾不上。** 勾了也跑不起来，只会在执行时白报一次错。

**存在 `checklists.json`**，记录 ``{清单名: [流程文件名]}`` 和当前选中的那份。存的是流程
文件名而不是绝对路径 —— 清单描述的是"要做什么"，不是"文件在硬盘哪个角落"。旧版的单清单
格式会自动迁移过来，不会因为升级丢掉已经勾好的状态。

**进模块编辑器时高亮的是操作区的「新建模块」按钮，不是任何导航项** —— 编辑器是二级页面，
跟「编辑流程」时侧边栏整个收起是一个道理。编辑已有模块也亮它，因为走的是同一个界面、同一件
事（写模块）。如果不这样，导航项会一直亮着，看起来像"这个导航一直选着"。

「我的模块」是一个**导航项**，点开是按列表列出的自己的模块 —— 和「插件」页同一种形态。
模块不在左侧栏里逐行铺开：左侧栏是导航，不是内容。改代码 / 重命名 / 删除这些操作都放在
**每一行上**，因为它们作用于某一行，而不是作用于整个页面。

### 每个页面都能切「网格 / 列表」

![插件页](docs/screenshot-plugins.png)

三个导航页面（我的流程 / 插件 / 我的模块）各自有一个**网格 / 列表**切换，按钮在**各自页面
的右上角**。

**为什么不放在全局菜单里。** "这一页怎么排"本来就是页面自己的事 —— 放全局意味着切个页还要
记得当前是哪种排法，而且三个页面共用一个开关也不合理（插件页想用网格、流程页想用列表是完全
正常的）。共用的是 `host/card_wall.py`：网格用 `FlowLayout`（固定尺寸方砖，摆不下换行），
列表用 `QVBoxLayout`（一行一条占满宽度）。

**切换时重建，而不是让控件在两种排法之间变形。** 两者的尺寸约束根本不同（固定尺寸 vs 撑满
宽度），让一个控件同时满足两边比各排一遍还麻烦，而且状态容易在两种模式之间漏掉。

「我的插件」页列的是随程序发出去的那批；「我的模块」页管自己写的（能改代码、能装依赖）。
**两边都能删**，而且**删除一律走回收站** —— 删的是用户自己的东西，误点的代价不该是"永久没了"。

走回收站用的是 `SHFileOperationW`（不是更现代的 `IFileOperation`：后者要先初始化 COM、
实现 `IShellItem` 那一串接口，为了删一个目录不值得）。非 Windows 上退回永久删除，
`to_recycle_bin()` 的返回值会说明到底发生了什么。

**内置插件也能删**，但有两道闸：内核的 `Registry.remove()` **默认拒绝**，只有显式传
`force=True` 才放开；界面上确认框会明说「这是程序自带的插件」，并且**把会受影响的流程列出来**
—— 流程按 id 引用插件，删掉一个内置的会让用到它的节点变成「插件未安装」。

**路径判据宁可窄。** `WorkflowLibrary.remove()` 只删流程目录里的文件，再往下走一层都不行；
`Registry.remove()` 同样只删插件目录里的目录。一个写错的 manifest 不该有机会删掉用户别的东西。

「打开文件」在顶部**文件菜单**里（`Ctrl+O`），「刷新」在**运行菜单**里（`Ctrl+R`）。

**两种展示方式，同一份数据：**

- **卡片**（`Ctrl+1`）—— **网格**。卡片固定尺寸，从左到右摆，摆不下自动换行，窗口拉宽就
  多放一张。Qt 没有内置这种流式布局（`QGridLayout` 要你事先知道列数，`QHBoxLayout` 不会
  换行），所以 `host/flow_layout.py` 自己实现了一个。
- **列表**（`Ctrl+2`）—— 一行一条，占满宽度。信息还是那些，但一屏能扫十几条。

两者是同一个基类（`EntryFrame`）的两个子类，共用状态徽标、运行态、双击执行逻辑 ——
不是两套实现，所以行为完全一致。

![列表视图](docs/screenshot-home-list.png)

三个刻意的取舍：

- **单击只是选中，运行要按「运行」或双击。** 自动化一旦跑起来会真的动鼠标键盘、真的写
  文件，让它被一次误点触发是不可接受的。"一键执行"省掉的是"打开画布再按 F5"，不是省掉
  所有确认。
- **同时只允许跑一条。** 运行期间所有卡片的按钮都禁用，而「停止」在两页都常驻可见 ——
  跑起来之后总得有地方能停下来。
- **坏文件也要显示出来。** 某条流程 JSON 被手改坏了、或者引用了没装的插件，用户最需要
  的是看到"第三条坏了、原因是这个"，而不是一个空白页面。坏卡片排到最后，运行按钮禁用，
  并直接写出原因。

### 插件页

![插件页](docs/screenshot-plugins.png)

命令行 `--list-plugins` 也能看到同样的信息，但那个输出是给开发者看的。这一页是给
"我想知道现在装着什么、每个能干什么"的用户看的：每个插件一块，列出它的动作/触发器、

### 自定义模块

左侧栏「自定义模块」下面列的就是它们 —— 用底部 AI 助手生成的，或者自己写好一个插件文件夹
丢进 `plugins/` 的。内置的六个在「插件」页，不在这里。

**增删改查**：

| | 怎么做 | 说明 |
|---|---|---|
| 增 | 操作列「新建模块」 | **直接切到右侧的代码界面**，用户在那边写 `main.py` |
| 删 | 右键「删除…」 | 停进程 → 删整个文件夹 → 刷新所有引用它的地方 |

### 模块代码界面

![模块代码界面](docs/screenshot-module-editor.png)

**不弹对话框。** 点「新建模块」直接开到这里 —— 用户要的就是一个能写代码的地方，中间加一层
"先填四个字段、点确定、然后才给代码框"只是多两步。

编辑器给的是三样东西：**行号**（没有它，"语法错误：第 37 行"这句话没法用）、**保存前校验**、
以及**错误行高亮**。校验做两件事：

- **标识合法性**（新建时）：格式、以及别跟已有模块撞。撞了会把别人的代码冲掉。
- **`ast.parse` 一遍**。语法错误的插件一旦落盘，注册表会把它标成"加载失败"，而失败现场是
  "我明明写好了"。在这里拦住，错误信息还能指到具体行列。

改已有模块走另一条路（`Registry.save_source`）：只覆盖 `main.py` 和那几个 manifest 字段，
**不整份重写 manifest** —— 用户完全可能自己往里面加了 `keywords`、`homepage`、`runtime.venv`
之类的字段，整份重写会把它们无声抹掉，而用户只改了一行代码，那种损失要过很久才会被发现。

### 为什么"改"不能改标识
 标识（id）是流程文件引用插件的方式。改了它，所有用到这个模块
的流程会立刻全部失效 —— 而用户看到的现象是"我的流程莫名其妙打不开了"，根本联想不到是那次
重命名。想换标识只有一个安全的做法：新建一个模块，把流程一个个搬过去。

**为什么删除要按这个顺序。** 停掉插件进程 → 删文件夹 → 刷新界面。Windows 上只要还有进程占
着目录里的文件（`__pycache__` 尤其容易被占），`rmtree` 就会抛 PermissionError；而那时注册表
已经把它删了，界面会显示一个"不存在但还在"的幽灵模块。删之前还会先数一遍**有多少条流程在用
它**，因为那是用户唯一能拿到的判断依据；删完那些流程显示「插件未安装」而不是打不开。运行中
禁止增删改。

**内置 / 自定义怎么区分。** 看 manifest 里的 `"builtin": true`。**默认当成"可删"是危险的
方向**，所以反过来：只有明确标了内置的才保护。这样用户手写的插件不需要额外登记，放进目录就
天然能被管理到。

`Registry.remove()` 另有一道防线：拒绝删除 `plugins/` 之外的任何路径 —— 一个写错的 manifest
不该有机会删掉用户别的东西。

### AI 助手

![AI 对话](docs/screenshot-ai.png)

底部「运行」面板的第四个页签，和运行日志、变量、运行历史并排 —— 它们回答的是同一类问题：
"现在发生了什么，接下来该做什么"。

**接的是真的模型**，走 OpenAI 兼容的 `/chat/completions`，配置在**顶部「编辑 → AI 设置…」**：

![AI 设置](docs/screenshot-ai-settings.png)

| 项 | 说明 |
|---|---|
| 接口地址 | 默认 `https://api.deepseek.com/v1`。带不带结尾斜杠、有没有写全 `/chat/completions` 都认 |
| API Key | 也可以改设环境变量 `MYAUTOWORK_AI_KEY`，**程序优先用环境变量** |
| 模型 | 默认 `deepseek-chat` |
| 温度 / 超时 | 一次调用几秒到几十秒，超时设太短会白等 |
| 系统提示词 | **默认那段就是插件的 SDK 说明书** —— 模型不知道这套 SDK 长什么样，只会写出一堆跑不起来的代码 |

**「测试连接」是这一页最重要的按钮。** 地址、模型名、密钥这三样里任何一样写错，症状都是
"AI 不回答"，光看对话根本分不出是哪一样。点一下让错误当场暴露。

#### 几个刻意的设计

**不引入 openai SDK。** 这个接口就是一次 POST 加一层 JSON，标准库 `urllib` 十几行就够。
为它拉依赖等于让所有用户多装一个包 —— 而可换的端点（DeepSeek、OpenAI、本地 Ollama、各种
中转）本来就是同一个形状。

**调用跑在线程里。** 一次几秒到几十秒，跑在主线程里界面整个冻住、连取消都点不了。
「正在想…」是个**占位气泡，不进历史** —— 记进去的话模型下一轮会看到自己"说过"这句话。

**同一句话只发一遍。** `AiPanel` 是先记用户消息、再调后端的，所以 `history` 最后一条就是
prompt；拼装消息时再追加一次的话，模型会收到两遍。它不报错，只会答得莫名其妙，很难往回查。
测试里专门有一条盯着这个。

**出错翻译成人话。** 用户看到 "HTTP 401" 不知道该干什么；看到"API Key 不对或者过期了，
去「编辑 → AI 设置…」看一眼"就知道下一步。这一层映射是后端代码里最主要的价值。
有些兼容端点把错误包在 200 里面，也检查了 —— 不检查的话会以 `KeyError` 收场，
把一个能说清的问题变成一句"没看懂"。

**密钥是明文存的**，面板上直接写明路径，并且告诉你可以改成环境变量。不掩饰这一点。

**AI 产出的插件先进草稿卡片，不直接写盘。** 插件是会读写文件、会操作界面的代码。
卡片上有代码预览、有校验结果，人点「保存到插件目录」才落盘。

**落盘前统一校验**（`kernel/authoring.py`）：id 合法性、名称非空、`main.py` 能不能通过
`ast.parse`。宁可拒绝，也不能写一个半坏的插件进去把注册表带崩。已有目录默认不覆盖 ——
AI 生成的东西撞上用户手写的插件时应该报错，而不是悄悄盖掉。

内核测试里有一条端到端的：草稿落盘 → `Registry` 重新发现 → 描述出接口 → **真的跑一次并
拿到返回值**。这才是"AI 能创建模块"的底线，而不是"两个文件写出去了"。

**测试不依赖你机器上的配置。** `MainWindow` 的 `ai_settings` 可以从外面传进来，
`ui_smoke` 传的是一份"没配过"的 —— 否则测试结果会取决于跑测试那台机器的
`%APPDATA%\myautowork\ai.json` 里有什么。

### 编辑器：画布

点某张卡片的「编辑」才进来。进来才出现模块面板和属性面板。

![编辑器](docs/screenshot-editor.png)

- **端口形态区分语义**：执行端口是三角，数据端口是圆点，颜色 = 数据类型
- **节点表头颜色 = 插件 category**，节点高度 = 端口行数，全部由接口声明算出
- 贝塞尔连线 + 箭头；错误出口用虚线
- 滚轮缩放、中键平移、框选、Delete 删除、`F` 适应窗口、`Ctrl+0` 复位
- 运行态：正在执行的节点发黄光、执行过的变绿并显示耗时角标、连过的边跟着变色

**连线规则在连线的那一刻执法**：执行连不上数据、类型不兼容、不能连到自己、一个数据
输入只能有一条入线（再连就替换并告诉你替换了哪条）。拒绝时给**具体原因** ——
"连不上但不知道为什么"是节点编辑器最劝退的体验。

面板用 `QSplitter` 排，不用 `QDockWidget`。停靠面板占的是 `QMainWindow` 的**顶层**区域，
会把自绘标题栏挤在中间：菜单只占一段、窗口按钮压在面板上、连拖窗口都只有中间能拖。

### 属性面板：schema 驱动

面板里没有一行代码认识具体插件。长什么样完全由插件声明决定：

| 插件声明 | 自动渲染 |
|---|---|
| `String / Number / Bool` | 输入框 / 数字框（带 min-max）/ 开关 |
| `Enum([...])` | 下拉框（选项直接来自声明） |
| `Text(multiline)` | 多行文本域 |
| `File / Folder` | 路径框 + **浏览**按钮 |
| `Element(picker="uia")` | 输入框 + **瞄准镜按钮** |
| `Code(lang=...)` | 等宽多行编辑器 |
| `list / dict / any` | JSON 编辑器（非法 JSON 标红，不静默吞掉） |

每个参数还带一个**取值来源**下拉：`常量 / 表达式 / 连线`。这是双线模型在界面上的落点 ——
用户点一下就能把写死的路径换成上一步的输出，不用改工作流结构。没有连线的输入，"连线"
选项是禁用的，免得选出一个取不到值的东西。

### 一条硬规则：不在运行期弹模态框

自动化可能跑几分钟，日志是唯一的现场记录。用模态框报"运行失败"，用户第一反应是点掉它 ——
点掉之后才想起还没看日志。所以运行结果、校验错误、拾取器未实现这类信息一律进日志面板和
状态栏。（只有"文件打开失败""未保存就要退出"这种必须现在决定的事才用对话框。）

## 架构

```
┌─ Host（PySide6 桌面壳）─────────────────────────┐
│  首页流程列表 · 画布 · 模块/属性面板 · 日志       │
│  全局热键 · 托盘 · 元素拾取瞄准镜（第 3 步）      │
└────────────────────┬────────────────────────────┘
                     │ 同进程调用（运行在 QThread 里）
┌────────────────────▼────────────────────────────┐
│  Kernel（不可插拔，保持薄）                      │
│  registry · engine · graph · expr · store · library │
└──┬───────────┬───────────┬──────────────────────┘
   │ stdio JSON-RPC（每个插件一个进程，可有自己的 venv）
┌──▼────┐  ┌───▼───┐  ┌────▼───┐
│worker │  │worker │  │worker  │
└───────┘  └───────┘  └────────┘
```

**界面是内核的消费者，不是内核的一部分。** 它读的是同一份插件接口描述、同一份工作流
JSON、同一套运行事件：

| 界面部分 | 数据来源 |
|---|---|
| 首页流程列表 | `kernel.library.WorkflowLibrary` —— 扫目录 + 关联运行历史 |
| 左侧模块面板 | `registry.catalog()` —— 插件声明了什么能力 |
| 右侧属性面板 | `node_spec()["inputs"]` —— 参数类型 → 自动生成控件 |
| 画布 | `kernel.graph.Workflow` —— 双线模型 |
| 运行态高亮 / 日志 / 变量 | `Engine(on_event=...)` |

所以界面里没有一行"某某插件"的特判。**装一个新插件，界面一行都不用改。**

**为什么插件要跑在独立进程里？**（假定所有插件都是安全代码，所以**不是**为了安全）

1. **界面不能卡。** UIA 调用经常阻塞好几秒。放主进程里，图形界面会直接冻住。
2. **依赖不打架。** 两个插件分别依赖 `requests` 2.1 和 2.31 是迟早的事。
3. **真并行。** Python 的 GIL 让主进程里跑多个自动化任务没意义，独立解释器才行。

协议用 stdio 而不是 socket：不占端口、不触发防火墙、进程一死管道立刻 EOF（健康检查
免费）、生命周期天然绑定。

### 模块职责

| 模块 | 职责 |
|---|---|
| `myautowork/` | **插件 SDK。** 插件作者唯一需要 `import` 的东西 |
| `kernel/manifest.py` | 静态描述：不执行插件代码就能知道它是谁 |
| `kernel/registry.py` | 插件发现、按需拉起进程、接口缓存与交叉校验 |
| `kernel/rpc.py` | 内核侧 RPC 客户端（含超时强杀、崩溃处理） |
| `kernel/worker.py` | 插件侧运行时（把 stdout 让给协议，插件里的 `print` 变成日志） |
| `kernel/graph.py` | 工作流模型 + 静态校验 |
| `kernel/expr.py` | 表达式求值（常量 / 变量 / 上游输出） |
| `kernel/engine.py` | 执行流 + 数据流双线引擎 |
| `kernel/store.py` | SQLite 运行历史（线程安全） |
| `kernel/library.py` | 工作流库：扫描目录、关联最近一次运行 |
| `kernel/authoring.py` | 插件草稿：校验 + 落盘（AI 创建模块的基础） |
| `kernel/run.py` | 命令行运行器 |
| `host/workflow_list.py` | 首页：网格卡片 + 通栏列表两种排法（共用一个基类） |
| `host/flow_layout.py` | 流式布局（卡片墙靠它换行） |
| `host/plugin_view.py` | 插件页：把插件目录摊开给人看 |
| `host/sidebar.py` | 左侧导航栏：切页 + 新建 |
| `host/ai_panel.py` | AI 对话面板（可替换后端 + 后台线程 + 插件草稿卡片） |
| `host/ai_backend.py` | OpenAI 兼容接口的调用与错误翻译 |
| `host/ai_settings.py` | AI 设置（含默认的系统提示词：插件 SDK 说明书） |
| `host/ai_settings_dialog.py` | 「编辑 → AI 设置…」那个窗口 |
| `host/titlebar.py` | 自绘标题栏：菜单 + 窗口按钮 + 拖动 |
| `host/canvas/` | 自绘画布：端口、节点、连线、视图 |
| `host/forms/` | **schema → Qt 控件**的自动表单生成器 |
| `host/panels/` | 模块面板、属性面板、日志/变量/历史面板 |
| `host/runner.py` | 后台线程跑工作流，事件转成 Qt 信号 |

## 执行模型：执行流 + 数据流双线

模型的核心是**两种边**：

- **exec 执行边**（灰白实线 + 箭头）：决定"先做谁后做谁"。**只有它驱动执行。**
- **data 数据边**（彩色曲线）：只表示"这个输入从哪取值"，不会让任何节点跑起来。

界面自动化是严格时序的，所以主线必须是 exec 流。纯数据流范式（Node-RED 那种）在这里
会失控。

五条规则：

1. 只有 exec 边驱动执行。
2. 执行节点前，先解析它的**全部**输入。
3. 节点输出缓存进 `$node.<id>.<port>`，**任何后续节点**都能用表达式取到 ——
   不必拉一根横跨半个画布的长线，画布能保持干净，跨分支取数据也不成问题。
4. 允许 data 边连到执行顺序更早的节点（静态判定不了，因为有分支和循环），
   运行时取不到值就**明确报错**，而不是给个 `null` 往下传。
5. 一个 exec 出口连多条线是**顺序执行**，不是并行。要并行必须显式用并行节点 ——
   界面自动化里隐式并行会造成几乎无法复现的 bug。

### 参数取值来源

参数存的不是"值"，而是"值从哪来"：

```jsonc
"params": {
  "timeout": 10,                                              // 常量（简写）
  "path":    {"mode": "expr", "value": "out/{{$date}}.txt"},  // 表达式
  "content": {"mode": "upstream"}                             // 来自连到该输入的数据边
}
```

### 内置变量

`$now` `$date` `$time` `$datetime` `$timestamp` `$run_id` `$workflow` `$workflow_id` `$workdir`
，外加工作流变量（`$vars.名字` 或直接 `$名字`）和节点输出（`$node.<节点id>.<端口>`）。

> 内置时间变量在**运行开始时快照一次**。所以同一轮运行里 `{{ $date }}` 始终一致 ——
> 跨午夜运行也不会出现"一半文件在昨天、一半在今天"。
> 整段文本恰好是一个 `{{ }}` 时返回**原始对象**而不是字符串。

### 错误处理与停止

每个节点有两个执行出口：`success` 和 `error`。

- `error` **没连线** → 向上冒泡，整条流程标记失败，后续节点不执行
- `error` **连了线** → 走错误分支，整次运行仍算成功，`$error` 里带
  `{node_id, type, message}` 供分支引用

停止的语义是**当前节点跑完就停**，不强杀插件进程 —— 一个正在点鼠标的动作被半路掐掉，
可能把目标程序留在半操作状态，比多等几秒糟得多。

## 写一个插件

插件就是一个目录，两个文件。

### 1. `manifest.json` —— 静态、可秒读

```json
{
  "id": "core.file.write",
  "name": "文件",
  "version": "0.1.0",
  "api_version": "1",
  "description": "文本文件读写。",
  "category": "文件",
  "runtime": { "type": "python", "entry": "main.py" },
  "provides": { "actions": ["write"], "triggers": [] }
}
```

`id` 必须和目录名一致。`provides` 会与实际注册的装饰器**交叉校验** —— 声明了却没写、
写了却没声明，都会在加载阶段报错，而不是让用户遇到"面板里有、点了报错"。

> 为什么要拆成两半？因为界面需要在**启动任何插件进程之前**把模块面板画出来。
> manifest 负责身份，装饰器负责完整的输入输出 schema。

### 2. `main.py` —— 用装饰器声明接口

```python
from myautowork import action, Context, File, Text, Enum, Bool, String, Integer

@action(
    id="write",
    name="写文件",
    category="文件",
    inputs={
        "path":     File(picker="save", required=True),
        "content":  Text(required=True),
        "encoding": Enum(["utf-8", "gbk"], default="utf-8"),
        "append":   Bool(default=False),
    },
    outputs={"path": String(), "bytes": Integer()},
)
def write(ctx: Context, path, content, encoding="utf-8", append=False):
    """把文本写入文件。"""
    target = ctx.resolve(path)
    ctx.info(f"写入 {target}")
    ...
    return {"path": str(target), "bytes": len(payload)}
```

### 3. 插件里必须遵守的几条

- **需要的一切从 `ctx` 拿。** `ctx.log/info/warn/error`、`ctx.progress()`、`ctx.vars`、
  `ctx.resolve(path)`、`ctx.artifact(name)`。这样日志自动带节点和运行编号。
- **相对路径走 `ctx.resolve()`。** 各插件自己猜 cwd 的话，"文件写到哪去了"会变成永久性谜题。
- **返回值必须是 `dict`**，键名与 `outputs` 声明一致。
- **可以用 `print`。** worker 会把 stdout 让给协议、`print` 自动变成 stderr 日志。
- **依赖放插件自己的 `.venv`。** 存在 `<插件目录>/.venv/Scripts/python.exe` 时会自动使用。

### 4. 长驻触发器（后续）

`@trigger` 已经用 `one_shot` 区分了两种形态。当前只有"一次性"触发（内核调用它一次）。
定时 / 热键 / 文件变化这类长驻触发器以后由内核启动、自己推事件回来，契约不需要改。

## 工作流格式

```jsonc
{
  "id": "demo",
  "name": "演示：等待后写文件",
  "description": "流程列表上显示的就是这一段。",
  "variables": { "greeting": "你好，myautowork" },
  "nodes": [
    { "id": "n1", "plugin": "core.trigger.manual", "action": "start",
      "pos": [60, 240], "params": { "note": "命令行验收" } },

    { "id": "n2", "plugin": "core.time.delay", "action": "sleep",
      "pos": [340, 240], "params": { "seconds": 1.5,
        "reason": { "mode": "expr", "value": "{{ $greeting }} —— 等界面加载" } } },

    { "id": "n3", "plugin": "core.file.write", "action": "write",
      "pos": [640, 110], "params": {
        "path":    { "mode": "expr", "value": "out/demo_{{$date}}.txt" },
        "content": { "mode": "upstream" } } }
  ],
  "edges": [
    { "from": "n1", "to": "n2", "kind": "exec" },
    { "from": "n2", "to": "n3", "kind": "exec" },
    // 数据边：把 n2 的 finished_at 输出接到 n3 的 content 输入
    { "from": "n2", "from_port": "finished_at",
      "to": "n3", "to_port": "content", "kind": "data" }
  ]
}
```

`id` 同时也是运行历史里的键 —— 首页卡片上的"上次运行结果"就是靠它关联的。
`kind: "exec"` 时可写 `"from_port": "error"` 指定走错误出口。

**写坏的边会在运行前就被拦下来**：悬空节点、不存在的端口、类型不兼容、必填输入没着落、
`upstream` 参数却没有连线、执行环 —— 都会在校验阶段报出来。

## 界面自动化

三个插件，各管一层：

| 插件 | 动作 | 管什么 |
|---|---|---|
| `win.window` | 激活 / 等待 / 列出 / 关闭 / 移动 / 信息 | 把目标窗口弄到前台。**不做这一步就点，点到的是你自己那个窗口** —— 这是最常见的自动化事故，而且现场看起来像"坐标算错了" |
| `win.uia` | 查找 / 点击 / 读取 / 写入 / 等待 / 聚焦 | 按定位器找界面元素并操作它 |
| `win.input` | 点击 / 输入 / 按键 / 滚动 / 拖拽 / 鼠标位置 | 底层键鼠，只知道屏幕坐标 |

### 元素定位器：五级降级

`Element` 类型的参数值是一份**带降级方案的定位描述**，不是坐标字符串。拾取时把能拿到的信息
全记下来，运行时按可靠性从高到低依次尝试，第一个命中的就用：

| 级别 | 依据 | 什么时候会失效 |
|---|---|---|
| `AutomationId` | 开发时写死的控件 id | 开发改了 id |
| `名称 + 控件类型` | 可见文字 + 控件类型 | 文案改了 / 多语言 |
| `相对路径` | 从窗口往下的父子链（类型+名字+序号） | 布局改了 |
| `图像匹配` | 截图匹配 | 分辨率 / 主题变了 |
| `坐标` | 绝对坐标 | 窗口一移动就废 |

后两级是兜底：屏幕上的东西最终总能"在某个位置画着"，所以只要有坐标就一定能点到。代价是脆，
所以排最后 —— 而且**用的是哪一级会明确报出来**。一条流程靠坐标跑通了，用户有权知道自己在走
钢丝：下次窗口挪一下它就会点到别的地方，而且不会报错。

### 拾取器

用户不可能手写 AutomationId —— Qt 程序的 AutomationId 是「应用名.窗口名.控件名」拼出来的
（实测：`QApplication.testRoot.okButton`），窗口名一改就全变。所以定位器**必须**由拾取器产出。

**交互为什么是"移动 + 点采集"而不是"直接点目标"。** 后者更直觉，但要吞掉那次点击 —— 否则你
在拾取的同时也把目标按钮按了。吞点击需要装全局鼠标钩子，那是一条又长又脆的路。现在的做法是：

1. 鼠标自由移动，一个**只画边框的透明置顶窗口**跟着光标框住它下面的元素
2. 抬眼看面板确认框对了
3. 点「采集」

代价是多一次点击，换来的是**永远不会误触发目标界面**。对一个会真的去点鼠标键盘的工具，这个
取舍值得。边框窗口只画边框而不是整块遮罩，是因为遮罩会盖住目标本身，而且会挡住我们用来找控件
的那一个光标点。

### 一个环境相关的坑：DPI 缩放

`myautowork/dpi.py` 在**每个进程入口最开头**开启 DPI 感知。不开的话 Windows 会把我们的坐标系
"虚拟化"：

```
真实分辨率        2560 x 1440
GetSystemMetrics  2048 x 1152   ← 进程 DPI 不感知时看到的
屏幕截图          2560 x 1440   ← 物理像素
```

两个坐标系差 1.25 倍，于是 **UIA 给出的元素矩形和截图裁出来的区域根本不是同一块地方** ——
图像匹配会自信地找到一个完全错误的位置。这个坑隐蔽在于**单看每个 API 都"正常"**，只有把 UIA
坐标和屏幕截图放在一起才会暴露；而且它在 100% 缩放的机器上永远不会犯。

`imaging` 另外做了坐标换算作为第二道防线：万一某个进程没能开成 DPI 感知，它按「截图尺寸 /
系统尺寸」自己算出缩放比。
